## Decisions

- **`profiles` select is own-row only in M1.** The design's select policy is `id = auth.uid() or shares_workspace(id)`, but `shares_workspace` needs `workspace_members`, which M2 adds. M2 widens the policy and its tests.
- **The 2FA restrictive policy (`mfa_opt_in`) is not on `profiles` yet.** It needs `private.mfa_ok()`, which M4 adds to every app table at once.
- **The trigger function is `private.handle_new_user()`, not `public`.** The design's RPC table lists it with the RPCs. It is a trigger, not an RPC, so it lives where PostgREST can't see it (checked: `POST /rest/v1/rpc/handle_new_user` returns `PGRST202`, not found). Nobody has execute on it, and a trigger doesn't need it: a real sign-up, which writes `auth.users` as `supabase_auth_admin`, created the profile with no grant to that role (see below).
- **The trigger reads nothing from the client.** `display_name` starts as `''` and the user sets it afterwards through the column-level update grant. Copying it from `raw_user_meta_data` would let a sign-up request put unchecked text in the table, and a name over 80 characters would make sign-up fail with a server error. Checked: a sign-up sending `"data":{"display_name":"evil"}` got a profile with an empty name.
- **Only `display_name` is updatable.** `grant update (display_name)`, so `id` and `created_at` can't be changed even on the user's own row, and the update policy's `with check` is a second guard on `id`.
- **No insert or delete grants.** Rows come from the trigger and go with `on delete cascade` from `auth.users`.

## Auth flow: sign-up, login, logout, reset, proxy and CSP

### Decisions

- [ADR 0014](../adr/0014-server-side-auth.md): auth runs only in Server Actions; session cookies are HttpOnly, SameSite=Lax and, over HTTPS, `Secure` with the `__Host-` prefix; `src/proxy.ts` sets a per-request nonce CSP and refreshes sessions; every page renders per request (root layout `instant = false` + `await connection()`), because a prerendered shell carries no nonce (measured 0 of 14 scripts).
- Email links go to `/auth/confirm?token_hash=…&type=…` and are verified only when the user presses the button (POST), so link scanners can't use them up. Templates in `supabase/templates/`; the M5 wizard must set the same templates and auth settings on hosted projects.
- `supabase/config.toml`: `enable_confirmations = true`, `minimum_password_length = 10`, `otp_expiry = 600`, `max_frequency = "60s"`.
- `?next=` after login accepts only same-site paths (`src/lib/auth/redirect.ts`).
- The app pages give one answer whether or not an email has an account: sign-up for an existing address shows the same "check your email" notice (Supabase answers 422 `user_already_exists`, measured), reset always shows "If an account uses that email…", and wrong email or wrong password both show "Wrong email or password."
- A password change ends the account's other sessions. Supabase Auth already does this (`UpdatePassword` calls `LogoutAllExceptMe`, [models/user.go at v2.197.0](https://github.com/supabase/auth/blob/v2.197.0/internal/models/user.go)), so the app adds no code for it; an E2E test guards it. A first version called `signOut({ scope: "others" })` as well; a planted removal showed it was redundant, so it was taken out.
- The design doc lists `/settings` among protected routes; the proxy already guards it for M4.

### Threat model (sign-up, login, reset, session)

| Threat | Control | Test |
|---|---|---|
| Session token stolen by injected script | HttpOnly cookie; nonce CSP with `strict-dynamic`, no `unsafe-inline`/`unsafe-eval` in production | E2E: cookie flags, `document.cookie` has no session; CSP header and nonce on every script, no CSP violations |
| Session cookie sent over plain HTTP or to other hosts | Over HTTPS: `Secure`, `__Host-` prefix, `Path=/`, no `Domain` | E2E: login replayed with `X-Forwarded-Proto: https` |
| Login CSRF / cross-site form posts | Next.js Server Actions compare Origin with Host; `SameSite=Lax`; CSP `form-action 'self'` | E2E: login replayed with `Origin: https://evil.example` gets 500 and no cookie; same replay from our origin signs in |
| Open redirect after login | `safeNext()` accepts same-site paths only | E2E: `https://evil.example/`, `//evil.example/`, `/\evil.example`, `javascript:` all land on `/w` |
| Account enumeration through the app's pages | Same message for known and unknown emails on sign-up, login and reset | E2E: duplicate sign-up (same notice, no email), unknown reset, unknown login |
| Confirmation or reset link used twice, or by a mail scanner | One-time token hash, verified on POST only; 10-minute expiry | E2E: replayed link refused; opening the link alone doesn't confirm |
| Login before confirming the email | `enable_confirmations = true` | E2E |
| Sign-up leaves a user with no profile | PR 9's trigger | E2E: after a real sign-up, the user's own token reads exactly one profile row (`display_name` empty) through the API |
| Weak passwords | 10-character minimum, enforced by Supabase Auth | E2E: 5-character reset password refused with the browser check turned off |
| Old sessions after a password reset | Supabase revokes the account's other refresh tokens | E2E: the other browser is signed out at its next refresh |
| Session stays usable after logout | `signOut({ scope: "local" })` revokes the refresh token and clears the cookies | E2E: cookies gone, `/w` redirects to login |
| Expired access token | Proxy refreshes it and writes rotated, hardened cookies | E2E: forced expiry, refresh token rotated, cookie still HttpOnly |
| Brute force and floods | Supabase Auth rate limits; the page shows "Too many attempts, try again later." on any 429 | E2E: real 429 from `max_frequency`; per-IP limits unverified (see below) |

### Hosted rate-limit test and the limiter (ADR 0015)

Hosted, on `porchlet-test` through the Vercel preview, 2026-11-23, run by Gobbu (`scripts/hosted/`):

- **App, before the limiter.** The 11th scripted wrong login got "Too many attempts". After that, a phone on mobile data got it on its first try. All visitors share Supabase's per-IP limit, because Supabase sees only the server's IP.
- **Direct to Supabase with the publishable key.**
  - A spray of 10 attempts got 10 × 400.
  - A throttle run of 40 got 22 × 400, then 18 × 429.
  - Fake `Sb-Forwarded-For` got 5/5 429, and fake `X-Forwarded-For` got 5/5 429. Supabase ignores `Sb-Forwarded-For` without a secret key, as documented.
- **ACAO.** `Access-Control-Allow-Origin: *` came back on `/`, `/login`, `/w` (redirected to `/login`) and `/api/health`, before and after the limiter. Vercel adds it; locally the app sends none. Checked below.

The fix, Porchlet's own limiter, has four kinds of test:
- **DB tests:** `020_rate_limit.test.sql` (16 checks).
- **E2E** in `e2e/rate-limit.spec.ts`:
  - an account blocked from one IP only;
  - an IP blocked with others unaffected;
  - sign-up limited per IP.
- **Per-test IPs:** every E2E test sends its own made-up `X-Forwarded-For` (`e2e/support/test.ts`), so tests don't share buckets.
- **Hosted re-test** (preview `ff23996` on `porchlet-test` with `RATE_LIMIT_KEY` set, 2026-11-23, run by Gobbu):
  - The laptop script got 5 × "Wrong email or password." then "Too many attempts" on try 6 (`firstTooMany: 6`).
  - Straight after, a phone on mobile data got 5 × "Wrong email or password." and "Too many attempts" only on its own 6th try.
  - So each visitor IP now has its own bucket. Before the limiter, the phone was blocked on its first try.

**ACAO=\* checked against signed-in pages** (measured locally, Chromium 1243). A proxy in front of `next start` added `Access-Control-Allow-Origin: *`, as Vercel does. A signed-in browser then fetched `/w` from a page on another site:
- `credentials: "include"` was blocked: "must not be the wildcard '*' when the request's credentials mode is 'include'".
- Without credentials, the browser sent no cookie and got the `/login?next=%2Fw` redirect, with no signed-in content.
- Control: `/api/health` was readable.

The `SameSite=Lax` session cookie also keeps cross-site fetches signed out. So the header exposes only what a signed-out visitor sees.

**HTTPS detection and the nonce on Vercel** (preview `ff23996`, fetched through the Vercel connector, 2026-11-24):
- The `/login` CSP ends in `upgrade-insecure-requests`, which the proxy adds only when `isHttps()` sees `X-Forwarded-Proto: https`. The session cookie takes `Secure` and the `__Host-` prefix from the same function. The cookie itself was not seen on Vercel.
- Two fetches about 46 s apart both came back `x-vercel-cache: HIT` with `x-nextjs-prerender: 1`, yet had different nonces (`4ELQ…` and `PriI…`). Each body used only its own header's nonce, checked by eye.
- The cached part is the partial-prerender shell, which is empty (0 bytes in `.next/server/app/login.html`, measured locally). Its saved resume state holds no nonce, so everything visible renders per request.

### Gaps

- **Hosts that don't overwrite `X-Forwarded-For`** let a client pick its own rate-limit bucket (ADR 0015); only Supabase's shared backstop applies there. Vercel overwrites it.
- **Supabase's own limits are not raised yet.** ADR 0015 keeps them as a backstop. The M5 setup wizard sets them; how high the free plan allows is unverified. Until then, a botnet spread over many IPs can still use up the shared limit.
- **Local Supabase Auth enforces no per-IP limits** (36 failed logins, no 429), so local throttle results come from Porchlet's limiter only.
- **Supabase Auth's API reveals which emails have accounts** to anyone with the publishable key: sign-up answers 422 `user_already_exists` for a confirmed address, and a second reset request inside 60 s answers 429 only for real accounts (measured). The app's pages hide this; the public API doesn't. Not fixable in the app.
- **No common or breached password check** (ASVS 6.2.4 L1, 6.2.12 L2). Supabase's leaked-password protection is a paid-plan feature (unverified). Proposed follow-up: check new passwords in the Server Action against a bundled top-passwords list and optionally the HIBP range API.
- **Session lifetime limits** (ASVS 7.1.1, 7.3.1, 7.3.2 L2) are not set or documented. Refresh tokens don't expire by default; Supabase's session time-box and inactivity timeout are paid-plan settings (unverified). To decide with M4.
- ~~Without JavaScript, form errors don't show (login and logout still work).~~ Closed by ADR 0018 (see "Form messages before hydration and without JavaScript" below).
- After a form is sent without JavaScript (or before the page hydrates), the email field comes back empty, and reloading the page shows the message again (ADR 0018).
- Build assets (`/_next/static`), `/_next/image` and `/favicon.ico` skip the proxy, so they get no CSP from it. `next.config.ts` gives exactly those paths `frame-ancestors 'none'`; its list must match the proxy matcher.
- Supabase Auth logs `Invalid Refresh Token: Refresh Token Not Found` to the server console when a revoked session hits the proxy; harmless but noisy.

## Form messages before hydration and without JavaScript

[ADR 0018](../adr/0018-native-form-posts-redirect-with-message.md). A form sent before React hydrated the page, or with JavaScript off, ran its action but showed no message: with Cache Components, Next.js 16.4.6 renders the response to a native form post by resuming the prerendered shell, and React's `resume()` takes no form state ([Next.js #99756](https://github.com/vercel/next.js/issues/99756)). It was the M1 "no-JS errors" gap. A Firefox E2E failure on PR 4 was put down to it; that test also types the same email twice, which hits the Firefox test-browser issue below, and it fails that way 3 of 60 times with default prefs, so either cause fits that run. Native posts now redirect back to the form's page with a message code, and the page shows that code's fixed text.

### Firefox: clicks lost to saved form history (test browser only)

Once Firefox has an email in its form history (typed and sent earlier in the same test, for example at sign-up), Playwright's headless Firefox sometimes drops the mouse press of the next click on the submit button. Only the release reaches the page, so there is no `click` and the form is never sent. The JavaScript-off flow that failed in CI types the sign-up email again on `/forgot`, and the page stayed there with the email filled in. The fix is test-only: `playwright.config.ts` turns off `browser.formfill.enable` for the Firefox project. Users keep form history; `autocomplete="off"` was not used, because real Firefox loses no clicks (below) and it would take saved emails and password managers away from users.

Measured on 2026-11-24 in the CI Playwright image (v1.65.1-noble, Firefox build 1572), 4 CPUs:

| Check | Lost clicks |
|---|---|

## RLS on private tables

[ADR 0017](../adr/0017-rls-on-private-tables.md). Migration `20261124000000_private_rls.sql` enables RLS, with no policies and without `FORCE`, on `private.instance`, `private.rate_limit_hits` and `private.rate_limit_key`. The API roles already had no schema usage and no grants; this is a third lock in case a later change grants a table or exposes the schema by mistake.

### Hosted

Applied to `porchlet-test` on 2026-11-24 through the Supabase connector (`execute_sql`, as `postgres`), before merge, because it only adds a lock on a test project and is undone with `disable row level security`. The three `alter table` statements ran; afterwards all three tables show RLS on, `FORCE` off. The security advisor listed the same two findings before and after (`rate_limit_hit` callable by `anon` and `authenticated`, which ADR 0015 intends), none about `private`.

Limiter on hosted with RLS on: Gobbu ran [`rls-limiter-probe.sql`](#hosted-limiter-probe) in the dashboard SQL editor on 2026-11-24 (screenshot). It swaps in a probe key, calls `public.rate_limit_hit` as `anon` with a wrong key and twice with the probe key, then raises an error so Postgres rolls back the whole block. Result: `P0001: PROBE as=anon wrong=<NULL> first=1 second=2 had_key=t (all rolled back)`. So with RLS on, the hosted limiter refuses a wrong key, counts hits, and the real key row was there before the probe (the rollback restores it).

The same probe was run on the local stack first, with a known key in place; afterwards that key was unchanged and no probe hits remained, which shows the rollback.

#### Hosted limiter probe

```sql
do $$
declare k bytea; a int; b int; w int; who text;
begin
  select key_hash into k from private.rate_limit_key;
  delete from private.rate_limit_key;
  insert into private.rate_limit_key (key_hash) values (extensions.digest('rls-probe-key', 'sha256'));
  set local role anon;
  who := current_user;
  w := public.rate_limit_hit('wrong', 'rls-probe', '203.0.113.9', 600, true);
  a := public.rate_limit_hit('rls-probe-key', 'rls-probe', '203.0.113.9', 600, true);
  b := public.rate_limit_hit('rls-probe-key', 'rls-probe', '203.0.113.9', 600, true);
  reset role;
  raise exception 'PROBE as=% wrong=% first=% second=% had_key=% (all rolled back)', who, w, a, b, k is not null;
end $$;
```
