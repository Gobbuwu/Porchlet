## Decisions

- **`profiles` select is own-row only in M1.** The design's select policy is `id = auth.uid() or shares_workspace(id)`, but `shares_workspace` needs `workspace_members`, which M2 adds. M2 widens the policy and its tests.
- **The 2FA restrictive policy (`mfa_opt_in`) is not on `profiles` yet.** It needs `private.mfa_ok()`, which M4 adds to every app table at once.
- **The trigger function is `private.handle_new_user()`, not `public`.** The design's RPC table lists it with the RPCs. It is a trigger, not an RPC, so it lives where PostgREST can't see it (checked: `POST /rest/v1/rpc/handle_new_user` returns `PGRST202`, not found). Nobody has execute on it, and a trigger doesn't need it: a real sign-up, which writes `auth.users` as `supabase_auth_admin`, created the profile with no grant to that role (see below).
- **The trigger reads nothing from the client.** `display_name` starts as `''` and the user sets it afterwards through the column-level update grant. Copying it from `raw_user_meta_data` would let a sign-up request put unchecked text in the table, and a name over 80 characters would make sign-up fail with a server error. Checked: a sign-up sending `"data":{"display_name":"evil"}` got a profile with an empty name.
- **Only `display_name` is updatable.** `grant update (display_name)`, so `id` and `created_at` can't be changed even on the user's own row, and the update policy's `with check` is a second guard on `id`.
- **No insert or delete grants.** Rows come from the trigger and go with `on delete cascade` from `auth.users`.

## Threat model (profiles)

| Threat | Control | Test (`010_profiles.test.sql`) |
|---|---|---|
| Reading another user's profile | Select policy `id = (select auth.uid())`; RLS on | 22, 23, 33 |
| Changing another user's profile | Update policy `using` and `with check` on `id`; select policy also filters `WHERE`/`RETURNING` | 25, 32 + 35 |
| Taking over another profile by changing `id` | No update grant on `id` | 10, 26 |
| Forging `created_at` | No update grant on `created_at` | 11, 27 |
| Creating or deleting profiles directly | No insert or delete grant | 13, 14, 28, 29 |
| Anonymous access | No `anon` grants | 7, 12, 34; baseline 2 |
| Calling the trigger function over the API | In `private`, no execute grant | 18, 19 |
| Search-path hijack in the `security definer` function | `set search_path = ''`, schema-qualified names | 17 |
| Oversized display name | `check (char_length(display_name) <= 80)` | 30, 31 |
| A user with no profile, or an orphan profile | Trigger on insert; `on delete cascade` | 20, 21, 36 |
| A permissive policy added later by mistake | `policies_are` lists exactly two; each checked for command, permissive and role | 5, 6 |

## How it was verified

Environment: Linux 6.18 x86_64 cloud container, Node 22, Docker 29.10.0, Supabase CLI 3.1.0 (repo pin), Postgres 17 from the CLI's image, `supabase start` with Auth and the API gateway, `supabase/pg_prove:3.36`.

| Check | Command | Result |
|---|---|---|
| pgTAP, clean database (as CI) | `supabase db reset`, then `supabase test db` | 2 files, 53 tests, `Result: PASS` |
| Count cross-check | `scripts/ci/db-count-check.sh` | 2/2 files, 53/53 tests, 2/2 tables covered |
| SQL lint | `supabase db lint --schema public,private --level warning --fail-on warning` | No schema errors |
| Real sign-up through Supabase Auth | `POST /auth/v1/signup` with the publishable key | HTTP 200; the profile row exists with `display_name = ''`. Auth's database session is `supabase_auth_admin` (`pg_stat_activity`), which has no execute on the function and no usage on `private`. |
| Through the API, as a signed-in user | `GET /rest/v1/profiles`; `PATCH /rest/v1/profiles?display_name=eq.` with two users both matching the filter | GET returned 1 row (own). PATCH changed only the caller's row; the other user's name stayed `''`. |
| Through the API, as `anon` | `GET /rest/v1/profiles` | `42501 permission denied for table profiles` |

pgTAP runs as `postgres`, which can't switch to `supabase_auth_admin`, so the test inserts into `auth.users` as `postgres`. The sign-up row above covers the real role. CI runs only `supabase db start` (no Auth service), so the sign-up check is manual here; the M1 sign-up E2E test will cover it in CI.

### Every test shown failing on a planted bad case

Each change was applied to the local database by hand, `supabase test db` run, and the change reverted.

| Planted case | Tests that failed |
|---|---|
| Select policy `using (true)` | 22, 23, 33 |
| Update policy `using (true) with check (true)` | 35 (test 32's blanket update reached B's row). Updates with a `WHERE` were still blocked by the select policy, which is why test 32 exists. |
| An extra permissive select policy | 5, 6, 22, 23, 33 |
| `grant update (id)` | 10 |
| `grant insert` | 8, 13, 14 |
| `grant delete` | 8, 13, 29 |
| `grant select ... to anon` | 7, 12, 34; baseline 2 |
| RLS disabled | 4, 22, 23, 25, 33, 35; baseline 1 |
| Trigger dropped | 20, 21, 22, 24, 30, 35 |
| `grant execute` on the trigger function | 19 |
| Function `search_path` reset | 17 |
| Length check dropped | 30 |

The first run of this table found that test 21 (the trigger made the two test profiles) counted every profile in the database, so it failed on a database that already had real sign-ups. It now looks only at the test users' ids.
