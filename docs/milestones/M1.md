## Decisions

- **`profiles` select is own-row only in M1.** The design's select policy is `id = auth.uid() or shares_workspace(id)`, but `shares_workspace` needs `workspace_members`, which M2 adds. M2 widens the policy and its tests.
- **The 2FA restrictive policy (`mfa_opt_in`) is not on `profiles` yet.** It needs `private.mfa_ok()`, which M4 adds to every app table at once.
- **The trigger function is `private.handle_new_user()`, not `public`.** The design's RPC table lists it with the RPCs. It is a trigger, not an RPC, so it lives where PostgREST can't see it (checked: `POST /rest/v1/rpc/handle_new_user` returns `PGRST202`, not found). Nobody has execute on it, and a trigger doesn't need it: a real sign-up, which writes `auth.users` as `supabase_auth_admin`, created the profile with no grant to that role (see below).
- **The trigger reads nothing from the client.** `display_name` starts as `''` and the user sets it afterwards through the column-level update grant. Copying it from `raw_user_meta_data` would let a sign-up request put unchecked text in the table, and a name over 80 characters would make sign-up fail with a server error. Checked: a sign-up sending `"data":{"display_name":"evil"}` got a profile with an empty name.
- **Only `display_name` is updatable.** `grant update (display_name)`, so `id` and `created_at` can't be changed even on the user's own row, and the update policy's `with check` is a second guard on `id`.
- **No insert or delete grants.** Rows come from the trigger and go with `on delete cascade` from `auth.users`.

## Auth flow: sign-up, login, logout, reset, proxy and CSP

### Decisions

- [ADR 0014](../adr/0014-server-side-auth.md): auth runs only in Server Actions; session cookies are HttpOnly, SameSite=Lax and, over HTTPS, `Secure` with the `__Host-` prefix; `src/proxy.ts` sets a per-request nonce CSP and refreshes sessions; every page renders per request (root layout `instant = false` + `await connection()`), because a prerendered shell carries no nonce (measured 0 of 14 scripts).
- Email links go to `/auth/confirm?token_hash=…&type=…` and are verified only when the user presses the button (POST), so link scanners can't use them up. Templates in `supabase/templates/`; the M5 wizard must set the same templates and auth settings on hosted projects.
- `supabase/config.toml`: `enable_confirmations = true`, `minimum_password_length = 10`, `otp_expiry = 600`, `max_frequency = "60s"`.
- `?next=` after login accepts only same-site paths (`src/lib/auth/redirect.ts`).
- The app pages give one answer whether or not an email has an account: sign-up for an existing address shows the same "check your email" notice (Supabase answers 422 `user_already_exists`, measured), reset always shows "If an account uses that email…", and wrong email or wrong password both show "Wrong email or password."
- A password change ends the account's other sessions. Supabase Auth already does this (`UpdatePassword` calls `LogoutAllExceptMe`, [models/user.go at v2.197.0](https://github.com/supabase/auth/blob/v2.197.0/internal/models/user.go)), so the app adds no code for it; an E2E test guards it. A first version called `signOut({ scope: "others" })` as well; a planted removal showed it was redundant, so it was taken out.
- The design doc lists `/settings` among protected routes; the proxy already guards it for M4.

### Threat model (sign-up, login, reset, session)

| Threat | Control | Test |
|---|---|---|
| Session token stolen by injected script | HttpOnly cookie; nonce CSP with `strict-dynamic`, no `unsafe-inline`/`unsafe-eval` in production | E2E: cookie flags, `document.cookie` has no session; CSP header and nonce on every script, no CSP violations |
| Session cookie sent over plain HTTP or to other hosts | Over HTTPS: `Secure`, `__Host-` prefix, `Path=/`, no `Domain` | E2E: login replayed with `X-Forwarded-Proto: https` |
| Login CSRF / cross-site form posts | Next.js Server Actions compare Origin with Host; `SameSite=Lax`; CSP `form-action 'self'` | E2E: login replayed with `Origin: https://evil.example` gets 500 and no cookie; same replay from our origin signs in |
| Open redirect after login | `safeNext()` accepts same-site paths only | E2E: `https://evil.example/`, `//evil.example/`, `/\evil.example`, `javascript:` all land on `/w` |
| Account enumeration through the app's pages | Same message for known and unknown emails on sign-up, login and reset | E2E: duplicate sign-up (same notice, no email), unknown reset, unknown login |
| Confirmation or reset link used twice, or by a mail scanner | One-time token hash, verified on POST only; 10-minute expiry | E2E: replayed link refused; opening the link alone doesn't confirm |
| Login before confirming the email | `enable_confirmations = true` | E2E |
| Sign-up leaves a user with no profile | PR 9's trigger | E2E: after a real sign-up, the user's own token reads exactly one profile row (`display_name` empty) through the API |
| Weak passwords | 10-character minimum, enforced by Supabase Auth | E2E: 5-character reset password refused with the browser check turned off |
| Old sessions after a password reset | Supabase revokes the account's other refresh tokens | E2E: the other browser is signed out at its next refresh |
| Session stays usable after logout | `signOut({ scope: "local" })` revokes the refresh token and clears the cookies | E2E: cookies gone, `/w` redirects to login |
| Expired access token | Proxy refreshes it and writes rotated, hardened cookies | E2E: forced expiry, refresh token rotated, cookie still HttpOnly |
| Brute force and floods | Supabase Auth rate limits; the page shows "Too many attempts, try again later." on any 429 | E2E: real 429 from `max_frequency`; per-IP limits unverified (see below) |

### Unverified

- **Per-IP rate limits on hosted Supabase with server-side auth.** Locally they never fire (ADR 0014). On hosted projects, auth calls come from the Next.js server's IP; whether all users then share one limit, and whether GoTrue's `Sb-Forwarded-For` is enabled and spoof-proof there, needs a test on the hosted throwaway project.
- Firefox and WebKit: covered by CI only.
- Vercel sets `X-Forwarded-Proto: https`, so cookies get `Secure` and `__Host-` there: to check on the preview deployment (cookies are not visible from this session, which can't open `*.vercel.app`).

### Gaps

- **SiegeKit and the local stack.** The design doc's threat model row 11 runs `login-throttle`, `login-spray`, `signup-limit` and `reset-limit` against the local stack, but local Supabase enforces no per-IP limits (36 failed logins, no 429). Those checks will report "not throttled" locally; run them against the hosted test project instead, and report it to SiegeKit if it doesn't say why.
- **Supabase Auth's API reveals which emails have accounts** to anyone with the publishable key: sign-up answers 422 `user_already_exists` for a confirmed address, and a second reset request inside 60 s answers 429 only for real accounts (measured). The app's pages hide this; the public API doesn't. Not fixable in the app.
- **No common or breached password check** (ASVS 6.2.4 L1, 6.2.12 L2). Supabase's leaked-password protection is a paid-plan feature (unverified). Proposed follow-up: check new passwords in the Server Action against a bundled top-passwords list and optionally the HIBP range API.
- **Session lifetime limits** (ASVS 7.1.1, 7.3.1, 7.3.2 L2) are not set or documented. Refresh tokens don't expire by default; Supabase's session time-box and inactivity timeout are paid-plan settings (unverified). To decide with M4.
- Without JavaScript, form errors don't show (login and logout still work).
- Build assets (`/_next/static`), `/_next/image` and `/favicon.ico` skip the proxy, so they get no CSP from it; the `frame-ancestors` header from `next.config.ts` (PR 8) must keep covering them.
- Supabase Auth logs `Invalid Refresh Token: Refresh Token Not Found` to the server console when a revoked session hits the proxy; harmless but noisy.
