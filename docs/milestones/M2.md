## 1. Scope

From the design doc (section 8, M2 row): tables `workspaces`, `workspace_members`, `invitations`, `projects`; their helpers, grants, RLS and RPCs; the invite page and invite email; pgTAP for every policy. **Done when** an owner invites a client, the client joins, and an outsider sees nothing. Then **full project check 1**.

In scope:

- Instance admin creates workspaces (`create_workspace`).
- Owner creates, renames and archives projects.
- Owner invites by email, revokes a pending invite, removes a client; a client leaves.
- New addresses get an invite email; addresses that already have an account get a link the owner copies (design, requirement 5).
- `profiles` select widens to co-members (`shares_workspace`), as M1.md promised.
- Owners see members' emails; clients see co-members' display names only (decision D3).

Not in M2: files, bucket and approvals (M3); TOTP, `aal2()` and `mfa_ok()` (M4, decision D1); the setup wizard and the admin claim (M5). Until M5, the admin is set by a documented SQL script on the local stack and `porchlet-test` only (decision D4).

## 2. Decisions

Each option was measured or compared on evidence; what wasn't measured is labelled.

### D1. Owner 2FA (`aal2()`) in M2 policies, or added in M4

The design's policies put `aal2()` on 8 owner actions in M2's tables (workspace rename, member removal, invite revoke, project insert, update and delete, `create_workspace`, `create_invitation`; counted from the design's policy and RPC tables). TOTP enrolment is M4.

| Option | Cost | Coverage |
|---|---|---|
| **A. Write M2 policies without `aal2()`; M4 adds `aal2()` and the restrictive `mfa_ok()` to every table in one migration** (recommended) | M4 touches the 8 sites, which it must also test with AAL1 claims anyway (M4's done-when: "owner writes fail with AAL1, pass with AAL2") | Owner actions accept AAL1 from M2 until M4. No release or real user before M6, so nobody is exposed. M2's E2E and R2 can use plain password sessions |
| B. `aal2()` now, and pull TOTP enrolment into M2 | M2 grows by M4's scope (design estimate 1 week, **unverified**) | Same end state, earlier |
| C. `aal2()` now, tested only with forged JWT claims in pgTAP | No extra build | M2's done-when can't pass in E2E (an owner can't act without TOTP), and R2 can't record owner writes. Fails the milestone |

Recommendation: **A**. C fails M2's own done-when; B costs about a week for no gain before release. Record the AAL1 window in M2.md's gaps and in the M4 plan.

### D2. How invite emails are sent (measured)

Measured 2026-11-24 on the local stack (Supabase CLI 3.2.0, `supabase/gotrue:v2.198.0`, `supabase/postgres:17.12.0.000`, Node 22.23.5, Docker 29.9.3, Linux cloud container), scripts in project files `porchlet-m2/invite-measure.mjs` and `invite-measure2.mjs`:

| Measurement | A. `auth.admin.inviteUserByEmail` (secret key) | B. No email: owner sends the link, client signs up | C. `signInWithOtp` from the server (publishable key) |
|---|---|---|---|
| New address | 1 email "You've been invited"; user created unconfirmed, no password | 0 emails from Porchlet; sign-up sends "Confirm your Porchlet account" | 1 email "Confirm your Porchlet account"; user created |
| Address with an account | `422 email_exists`, no email (owner copies the link, as the design says) | same as new | "Your sign-in link" email |
| Invite link works server-side | Yes: `verifyOtp({token_hash, type: "invite"})` gave an AAL1 session with the invited email, `updateUser` set a password, password login worked; reusing the link got `403 otp_expired` | n/a | Not measured |
| Second email to the same address within 60 s | **Sent** (2 emails in 14 ms): `max_frequency` doesn't apply to admin invites. Porchlet's own cap is the only limit | n/a | Not measured |
| Pending invite, then the person signs up on their own | Within 60 s: `429 over_email_send_rate_limit`. After 61 s: sign-up answers OK and sends a confirmation email, but **no password is stored** (`length(encrypted_password) = 0`) | n/a | n/a |
| Revoking a pending invite | `auth.admin.deleteUser` removes the pending user (needs the secret key) | Delete the row | Pending user stays |
| Secret key used | Yes (ADR 0005's invite route) | No | No |
| Hosted email | Needs the operator's SMTP (M5) | None | Needs SMTP; calls come from the server's IP, so all owners share Supabase's per-IP email budget (as R0h showed for logins) |
| Client steps, new address | Email button, set password, join | Get link, sign up, confirm email, log in, join | Confirm, set password, join |

Recommendation: **A**, the design's choice, now measured. It meets requirement 5 with the fewest client steps, and keeps the secret-key path that `served-secrets` and the CI grep should guard. B is the safest (no secret key, no email limits) but drops requirement 5's email. C saves the secret key but shares one per-IP email budget across every owner and sends the wrong template.

What A's measurements add to the build (PR 3):

1. Porchlet's invite cap (20 per owner per hour, 20 pending per workspace, in `create_invitation`) is the only limit on invite emails, so it needs a pgTAP and an E2E test.
2. A pending invite breaks self sign-up for that address (no password stored). The invite page must tell the person to use the email, and revoke and expiry must delete the pending Supabase user. Test both.
3. An `invite.html` template with the token hash, and `/auth/confirm` accepting `type=invite` and sending the person to set a password, then to the Porchlet invite.
4. The email link is built from a configured site URL, never the request's `Host` header.

### D3. How owners see who is in a workspace

`profiles` has no email, and `auth.users` isn't exposed. An owner needs to know who each member is.

| Option | Who sees member emails |
|---|---|
| **A. Owner-only `security definer` RPC returning members with emails** (recommended) | Owners of that workspace only |
| B. `email` column in `profiles`, kept in sync by a trigger | Every co-member, clients included |
| C. Display names only | Nobody; `display_name` starts empty (M1), so members can't be told apart |

Recommendation: **A**, the smallest exposure that still works. Compared on exposure only; build cost not measured (**unverified**).

### D4. Who is the admin before the M5 wizard

| Option | Risk |
|---|---|
| **A. `scripts/dev/make-admin.sql` sets `private.instance.admin_user_id`, local and `porchlet-test` only** (recommended) | None new; M5 replaces it |
| B. First user to sign up becomes admin | Open sign-up means anyone can race for it: takeover |
| C. Build the wizard's claim step now | Pulls M5 work forward |

### D5. Writes as Server Actions or as route handlers

| Option | Evidence |
|---|---|
| **A. Server Actions** (recommended) | Same as M1 (ADR 0014, ADR 0018). Next.js refuses a foreign `Origin` with HTTP 500 (measured in M1). Works without JavaScript. The usual Next.js pattern, so it tests SiegeKit on what real apps do |
| B. Route handlers (`/api/...`) answering 403 on refusal | SiegeKit's write check would read refusals more cleanly (see section 5), but each route needs its own Origin check, and the app gets two styles. Cost not measured (**unverified**) |

Recommendation: **A**. Where SiegeKit misreads Server Actions, that's a SiegeKit finding to report, which is Porchlet's purpose.

## 5. SiegeKit run due at M2: R2 (and R2b)

Where: local stack plus `next start` (a cloud session ran R1 this way). SiegeKit's latest `main`, commit recorded. Three accounts: A owner of workspace X, B client of workspace Y, C outsider; the session cookie on plain HTTP is `porchlet-auth`.

| Check | What it should show | What SiegeKit's code says in advance (read at 56f931b) |
|---|---|---|
| `access-control` (`--har` as A, `SIEGEKIT_SESSION_B`, `SIEGEKIT_SESSION_C`) | B and C get nothing of X | GET replay only; should work on Server Component pages. |
| `access-control-write` (`--replay-writes`) | Every replayed write refused | The design's unverified item is answered by the code: replays keep `Next-Action`, since only transport, `Proxy-*` and `Sec-*` headers are dropped (`internal/authz/authz.go:67`, `:272`). But a write counts as accepted on any 2xx, or a 3xx when A's write was also a 3xx and not to a login page (`internal/authz/write.go:1162`). A refused Server Action still answers 200 (React path, which returns the form state per ADR 0018; **unverified** for writes) or 303 to the same page with an error (no-JS path, as R1h saw for login). So **expect false medium findings**; a high one still needs A's read to change. Confirm in the run, then file a `from-porchlet` issue. Whether HAR keeps multipart bodies is **unverified**. |
| `rate-limit` on the invite action | Limited after 20 | `rate-limit` sends no session headers (`internal/ratelimit/ratelimit.go:233`, `send(...)` without session), and a first answer of 401, 403, 404 or 405 means "behind a login". The invite needs an owner session, and it's a Server Action (#81's class). **Expect it can't reach the limit**; Porchlet's pgTAP and E2E measure the cap. Confirm, then file an issue. |
| R0 set, `served-secrets`, SK-1 to SK-9 re-check, planted cases | As before; the new secret-key use must not reach `.next/static` | n/a |
| R2b `backend-live` | Every M2 table refused or empty for `anon` | Needed SiegeKit PR 73, which merged on 2026-11-24 (e4b3da0), so R2b runs with R2 using `SIEGEKIT_SUPABASE_KEY`. |

### What was built

- `supabase/migrations/20261125010000_workspaces.sql`: `workspaces`, `workspace_members`, `invitations` and `projects` as in the design, with RLS, column-level grants and 11 new permissive policies (no `aal2()`, decision D1); `private.invitation_sends`; the helpers `private.member_workspace_ids()`, `owner_workspace_ids()`, `co_member_ids()` (executable by `authenticated`) and `private.is_owner()` (not); the RPCs `create_workspace`, `create_invitation`, `accept_invitation` and `list_workspace_members` (decision D3); and `profiles_select_co_member`, which widens `profiles` select to co-members.
- `scripts/dev/make-admin.sql` (decision D4): makes an existing, confirmed account the instance admin, local stack and `porchlet-test` only.

Where it differs from the design, with the evidence (details in ADR 0006):

| Design | Built | Why |
|---|---|---|
| Policies call `is_member(ws)` per row | `ws in (select private.member_workspace_ids())` | All visible projects of 20,000: 123.9 to 132.2 ms per row, 1.3 to 1.6 ms set-based (5 runs each) |
| Hourly cap counted from `invitations.created_at` | Counted from `private.invitation_sends` | Owners can delete invitations, so revoking freed room under the cap (planted case P20) |
| Caps checked by counting | Counting under a workspace row lock (`for no key update`, so foreign-key inserts don't wait: a project insert took 0.045 s while a `create_invitation` held the lock) and a per-owner advisory lock; `repeatable read` refused | Without the locks two parallel calls both passed (P21a: 21 pending; P21b: 21 sends in the hour) |
| `accept_invitation` checks the JWT's email | Reads the caller's `auth.users` row (email and `email_confirmed_at`) | Current even when the JWT predates an email change |
| Owners select every `invitations` column | Every column except `token_hash` | Nothing needs it. Side effect: `select("*")` on `invitations` is refused (measured through PostgREST: `42501`), so PR 2 and PR 3 name their columns |
| `projects` insert grant on the table | Columns `workspace_id`, `name` only | The caller can't choose a project id or `created_at` |

## 13. Invite follow-up (full project check 1, F3 and F4)

Full project check 1 (project file `porchlet-check1/report-and-fix-plan.md`, fix plan step B) found that T9's E2E checks couldn't fail (F3): the browser reached the app as `127.0.0.1:3000`, the same value as `SITE_URL`, so a link built from the request would also have passed. ### What was built

- `e2e/invites.spec.ts`, new test "invite links stay on the site's URL when the app is reached by another host name": the owner logs in, creates a workspace and invites through `http://localhost:3000` while `SITE_URL` is `http://127.0.0.1:3000`. It checks that the page is still on `localhost:3000` (so the requests carried that Host), that the link the page shows is on `127.0.0.1:3000` right after the invite and again after a reload, and that the email's link is on `127.0.0.1:3000` and the invite link inside it (its `invite` parameter, the `redirectTo` the app sent) is the page's link.
- `e2e/support/invites.ts`: `inviteEmailLink` now also checks the `invite` parameter, for every invite test; the page-link check moved into `shownInviteLink`.
- Why the reload (measured, Next.js 16.4.6, `next start --hostname 127.0.0.1`): the action itself sees `Host: localhost:3000`, but the page render that follows the action's redirect sees `Host: 127.0.0.1:3000` (the server's own address) with `X-Forwarded-Host: localhost:3000`. A plain page load sees `Host: localhost:3000`. So a page that built the link from `Host` showed the right link right after the invite and the wrong one after a reload.
- `supabase/templates/invite.html`: "Signing up on your own with this address works too: a minute or more after this email, sign up, then press this button while logged in and choose \"Join workspace\". The button alone is quicker." That is the flow of the E2E "a pending invite, then the person's own sign-up", which waits 61 s because Supabase Auth refuses a second email to the address within `max_frequency` (60 s, `supabase/config.toml`; a sign-up sooner answers 429). Checked in Mailpit: the local stack's invite email carries the new text.
